# 構成テンプレート — 提案資料

社外に提出する提案資料（BtoB 提案・営業提案・研修提案・企画書）を作るときの内容要件と言葉遣い。

> **これは雛形ではない。** 下のブロック表は「提案として成立するために必要な要素」のチェックリストであって、
> 並び順でも枚数でもない。**構成は毎回、材料の内容から設計する**（`core/structure.md` §1）。
> 「表紙 → 課題 → 解決策」を固定の並びとして流し込むことは禁止。

---

## 1. ブロック定義

| | ブロック | 果たすこと |
|---|---|---|
| **必須** | 表紙 | 何の提案か・誰に宛てたか・いつのものか |
| **必須** | 課題 | 相手が困っている状態。**相手の言葉で書く**（こちらの商品説明にしない） |
| **必須** | 解決策 | 課題に対して何をするか |
| **必須** | 次の一歩 | 相手に何をしてほしいか（§3-2 の依頼形で書く） |
| 任意 | 原因分析 | 課題がなぜ起きているか。材料があるときだけ |
| 任意 | 事例 | 類似の実績。**架空の事例を作らない**（§2） |
| 任意 | 進め方 | フェーズ・体制図・役割分担 |
| 任意 | 体制 | 誰が担当するか |
| 任意 | 費用 | 見積もり。**§4 の位置ルールに従う** |
| 任意 | リスク | 想定される障害と対処 |

- **材料が無い任意ブロックは出さない。** 埋めるために内容を作らない
- **材料が無い必須ブロックは TODO ブロックとして出す**（§2）

枚数の目安は `core/structure.md` §2 を参照。

---

## 2. TODO ブロック

材料が無い必須ブロックは、**推測で埋めずに TODO として出す。**

提案資料には材料がないと書けないブロックがある（費用・体制・実績・スケジュール）。ここを AI が推測で埋めると、**実在しない金額や実績が載った提案書が、そのまま客先に持ち込まれる**。これは提案資料で最も避けるべき事故なので、埋めないことを規範にする。

### 2-1. 見た目（1 スタイルに固定する）

```html
<div style="border:1px dashed var(--line);border-radius:var(--radius);
            padding:28px 32px;color:var(--sub)">
  <div style="font-family:var(--ff-en);font-size:11px;letter-spacing:.14em;
              color:var(--dim);margin-bottom:10px">TO BE FILLED</div>
  <div style="font-size:18px;font-weight:700;color:var(--ink);margin-bottom:8px">
    ここにお見積もりを記入してください
  </div>
  <div style="font-size:14px;line-height:1.9">
    例: 初期費用・月額・期間・含まれる作業範囲
  </div>
</div>
```

- 破線の囲み ＋ 「TO BE FILLED」ラベル ＋ 何を書くかの指示 ＋ 例示 1 行
- 装飾しない。印刷しても TODO だと分かる見た目にする

### 2-2. 検証時の扱い

**TODO ブロックを含むスライドは、視覚検証の密度チェック・余白チェックの対象外**（`core/validation.md`）。この除外が無いと「内容が薄いので加筆する」判定が働き、検証ループ自体が TODO を埋める方向に圧力をかけてしまう。

### 2-3. 完了報告

TODO を出したら、**完了報告に一覧を必ず列挙する**。

> 3 枚が TODO です: お見積もり / 体制 / 導入スケジュール

## 3. 言葉遣い

### 3-1. 見出しは名詞型で書く

見出し（h2）は**短い名詞・名詞句**にする。文章にしない。

| 使わない（文章型） | 使う（名詞型） |
|---|---|
| 初期50万円＋月40万円の6ヶ月伴走で体制をつくります | **お見積もり** |
| 貴社が手を動かし弊社が伴走することでノウハウが残ります | **ご提案内容** |
| 分かれたシステムを人が繋いでいるため工数が集中しています | **現状の業務フロー** |
| まずはご担当者と確保時間をご決定ください | **次のステップ** |

よく使う語彙: ご提案の概要 ／ 現状の業務フロー ／ 課題の整理 ／ 課題と打ち手の対応 ／ 進め方 ／ ご提案内容 ／ 支援内容 ／ お見積もり ／ 費用対効果 ／ 期待効果 ／ 実績 ／ サポート体制 ／ 対象業務と適用範囲 ／ ロードマップ ／ スケジュール ／ 次のステップ ／ ご確認事項

- **主張・結論は本文側で言う。** 見出しには載せない
- 見出しに連番（①②③）を出さない。目次に見える
- KI ラベルは**章番号**にする（`SECTION 01` 〜、付録は `APPENDIX 01` 〜）。名詞見出しと意味が重複しないため

> 結論を全文で書く見出し（Action Title）を推す流儀もあるが、**このキットは名詞型を採る**。日本語の提案資料では見出しが長いと視線が止まり、読み手が本文へ進まないため。

### 3-2. 本文は敬体、依頼は依頼形

| | 使わない | 使う |
|---|---|---|
| 本文 | 工数がそこに集中している | 工数がそこに集中して**います** |
| 依頼 | 担当者の設置と確保時間の決定 | 担当者を設置いただき、確保できる時間を**ご決定ください** |
| 依頼 | 業務フローを整理し共有 | 業務フローを整理いただき、**ご共有ください** |

自社の行為は謙譲で書く（「ご説明します」「ご送付いたします」）。

### 3-3. 使わない語彙

読み手を受講者・見込み客として扱う語感になり、提案書として不自然になる。

- 「貴社が得るもの」「あなたが得られるもの」「得られる成果」
- 「→ WHY」「→ OUR RESPONSE」「→ EFFECT」「→ GOAL」などの英字ラベル帯
- 「〜しましょう」「〜してみてください」の呼びかけ（締めの 1 行だけは可）

代替: ラベルを外して上罫線＋補足文にする。ラベルが要るなら日本語の中立語（「補足」「前提」「ご参考」）。

### 3-4. 体裁

- 語中で行を分けない（「ご共有く／ださい」）。`<br>` で明示制御する
- 注記（※）はぶら下げインデントにして、2 行目以降を本文位置に揃える

## 4. 構成上の規範

- **金額を冒頭に出さない。** サマリー・概要ページに価格を載せず、費用ブロック（本編後半）で提示する
- サマリーは「現状 → ご提案 → 目指す状態」など**提案の輪郭**を示すにとどめる
- **渡された叩き台の見出しをそのまま使わない。** 議事録・メモ・ユーザーが書いた見出し案は「何を書く枚か」のメモであって最終形ではない。§3 に照らして必ず書き直し、直した箇所を完了報告に列挙する

## 5. preflight 追加検査（提案資料のとき必ず実行）

`core/rules.md` §12 に加えて実行する。**判定基準はいずれもヒット 0 件。**

```bash
# (P1) 文章型見出し
grep -nE '<h2[^>]*>[^<]*(します|ます|です|ください|できる|する|残る|つくる)</h2>' slides/*.html

# (P2) 見出しの連番
grep -nE '<h2[^>]*>\s*[①②③④⑤]' slides/*.html

# (P3) 使わない語彙
grep -nE '貴社が得るもの|あなたが得る|得られるもの|→\s*(WHY|OUR |EFFECT|GOAL|POINT)' slides/*.html

# (P4) 常体の言い切り（敬体に直す候補）
grep -nE '>[^<]*(できる|になる|残る|変わる|進める|行う|している|していた|した|ている|である|だ)</div>' slides/*.html

# (P5) 依頼形になっていないネクストアクション
grep -nE 'いただきたい|の決定</|を共有</' slides/*.html

# (P6) 金額が前半に出ていないか（前半 1/3 のスライドに金額表記）
perl -0ne '@s=/<div class="s\b[\s\S]*?(?=<div class="s\b|<\/body>)/g; $n=int(@s/3); for $i (0..$n-1){ print "スライド ".($i+1)." に金額表記\n" if $s[$i]=~/[0-9]+\s*(万円|円\/月|千円)/ }' slides/*.html
```

---

## 6. 完了報告に含めること

1. 叩き台から書き直した見出しの一覧（旧 → 新）
2. 言葉遣いを直した箇所（敬体化・依頼形化・ラベル削除）
3. TODO ブロックの一覧（§2-3）
4. §5 の検査結果
