# 構成テンプレート — 社内向け資料

社内で共有・報告・上申する資料（定例報告・企画共有・振り返り・決裁依頼）を作るときの内容要件と言葉遣い。

> **これは雛形ではない。** 下のブロック表は「社内資料として成立するために必要な要素」のチェックリストであって、
> 並び順でも枚数でもない。**構成は毎回、材料の内容から設計する**（`core/structure.md` §1）。

---

## 1. 提案資料との決定的な違い

| | 提案資料（`proposal.md`） | 社内向け資料（このファイル） |
|---|---|---|
| 起点 | **課題**から入る。相手の困りごとを示してから解決策 | **結論**から入る。何をどうしたいかを最初に言う |
| 相手の関心 | 「自社の課題が解決するか」 | 「**自分は何を判断すればいいか**」 |
| 締め | 次の一歩（相手に動いてもらう） | **決めてほしいこと**（決裁・合意・承認） |
| 敬語 | 丁寧に。依頼は依頼形で | **過剰敬語を避ける**。簡潔に |
| 背景説明 | 厚めに書く（相手は前提を知らない） | **薄くてよい**（前提は共有されている） |

**社内資料で最も嫌われるのは「結論が最後にある」構成。** 読み手は忙しく、最初の 1 枚で判断材料を求めている。

---

## 2. ブロック定義

| | ブロック | 果たすこと |
|---|---|---|
| **必須** | 表紙 | 何についての資料か / いつ / 誰が |
| **必須** | 結論 | **何をどうしたいか / どうなったか**を 1 枚で言い切る |
| **必須** | 根拠 | 結論を支える数字・事実・経緯 |
| **必須** | 決めてほしいこと | 読み手に何を判断・承認してほしいか（§4-2） |
| 任意 | 背景 | 前提が共有されていない相手がいる場合だけ |
| 任意 | 選択肢比較 | 複数案から選ぶ判断を求めるとき |
| 任意 | リスク | 想定される障害と対処 |
| 任意 | スケジュール | 期日・マイルストーン |
| 任意 | 費用 | 金額が判断材料になるとき |

- **材料が無い任意ブロックは出さない**
- **材料が無い必須ブロックは TODO ブロックとして出す**（§3）

### 2-1. 用途が細分化されるとき

「社内向け」は幅が広い。実際には次のどれかであることが多く、必須ブロックの重みが変わる。

| 種類 | 特に厚くする |
|---|---|
| 定例報告 | 根拠（数字の推移）。決めてほしいことは無いこともある |
| 企画共有 | 結論と根拠。決めてほしいことは「進めてよいか」 |
| 振り返り | 根拠（何が起きたか）＋ 次にどうするか |
| 決裁依頼 | **決めてほしいこと**を最も明確に。選択肢比較も添える |

**決めてほしいことが本当に無い資料（純粋な情報共有）では、このブロックを「今後の予定」に置き換えてよい。**
ただし「共有だけのつもりが実は判断を求めている」ケースが多いので、まず疑う。

## 3. TODO ブロック

材料が無い必須ブロックは、**推測で埋めずに TODO として出す。**

社内資料でも、実績値・予算・スケジュールを AI が推測で埋めると、**そのまま会議に出て意思決定を誤らせる**。
仕様は `proposal.md` §2 と同じ（破線囲み ＋「TO BE FILLED」ラベル ＋ 何を書くかの指示 ＋ 例示 1 行）。

```html
<div style="border:1px dashed var(--line);border-radius:var(--radius);
            padding:28px 32px;color:var(--sub)">
  <div style="font-family:var(--ff-en);font-size:11px;letter-spacing:.14em;
              color:var(--dim);margin-bottom:10px">TO BE FILLED</div>
  <div style="font-size:18px;font-weight:700;color:var(--ink);margin-bottom:8px">
    ここに実績値を記入してください
  </div>
  <div style="font-size:14px;line-height:1.9">
    例: 対象期間 ／ 件数 ／ 前期比 ／ 集計方法
  </div>
</div>
```

- **TODO ブロックを含むスライドは視覚検証の密度・余白チェックの対象外**（`core/validation.md`）
- 完了報告に TODO 一覧を必ず列挙する

## 4. 言葉遣い

### 4-1. 見出しは名詞型・本文は敬体・過剰敬語は避ける

見出しの原則は `proposal.md` §3-1 と同じ（**短い名詞・名詞句**にする。文章にしない）。ただし**語彙が違う**。

よく使う語彙: 結論 ／ 現状 ／ 実績 ／ 進捗 ／ 課題 ／ 原因 ／ 対応方針 ／ 選択肢 ／ 比較 ／ 判断のポイント ／ リスクと対処 ／ スケジュール ／ 体制 ／ 費用 ／ **決めていただきたいこと** ／ 今後の予定 ／ 補足

本文は敬体（です・ます）。ただし提案資料のような**過剰な敬語は使わない**。

| 使わない（社外向けの敬語） | 使う（社内向け） |
|---|---|
| ご提案いたします | 提案します |
| ご確認くださいますようお願い申し上げます | ご確認ください |
| 弊社／貴社 | 当社／〇〇部 |
| ご検討いただけますと幸いです | ご判断ください |

**箇条書きは体言止めでよい**（「対象範囲の確定」「担当者の指名」）。本文の文章だけ敬体にする。

### 4-2. 「決めてほしいこと」は具体的に書く

社内資料で最も価値があるのはこのブロック。**曖昧だと会議が空転する。**

| 使わない | 使う |
|---|---|
| ご検討ください | **A 案で進めてよいか**ご判断ください |
| よろしくお願いします | **10 月着手の可否**と**担当者 1 名の確保**をご承認ください |
| 引き続き進めます | 追加予算 〇〇円の要否を**今週中に**ご判断ください |

書くべき要素: **何を**（判断対象）／**誰が**（決裁者）／**いつまでに**（期限）。

### 4-3. 使わない語彙

- 「〜させていただきます」の連発（1 資料に 1 回まで）
- 「鋭意」「善処」「前向きに検討」など判断を先送りする語
- 社外向けの「貴社が得るもの」型のラベル

### 4-4. 体裁

- 語中で行を分けない。`<br>` で明示制御する
- 注記（※）はぶら下げインデント
- **数字には必ず単位と期間を添える**（「120 件」ではなく「月 120 件（2026 年 7 月）」）

## 5. 構成上の規範

- **結論を最初に置く。** 背景・経緯から始めない
- **背景ブロックは削れないか疑う。** 前提が共有されている相手には不要
- **判断に不要な情報は付録に回す。** 本編は「判断できる最小限」に絞る
- 選択肢を示すときは**推奨案を明示する**。「どれでもよい」は判断を丸投げしている
- **渡された叩き台の見出しをそのまま使わない。** 議事録・メモ・ユーザーが書いた見出し案は「何を書く枚か」のメモであって最終形ではない。§4 に照らして必ず書き直し、直した箇所を完了報告に列挙する

## 6. preflight 追加検査（社内向け資料のとき必ず実行）

`core/rules.md` §12 に加えて実行する。

```bash
# (I1) 文章型見出し（proposal と共通）
grep -nE '<h2[^>]*>[^<]*(します|ます|です|ください|できる|する)</h2>' slides/*.html

# (I2) 社外向けの過剰敬語
grep -nE 'ご提案いたします|お願い申し上げ|幸いです|弊社|貴社|ご査収' slides/*.html

# (I3) 判断を先送りする語
grep -nE '鋭意|善処|前向きに検討|引き続き検討' slides/*.html

# (I4) 「させていただ」の多用（2 件以上でヒット扱い）
grep -o 'させていただ' slides/*.html | wc -l

# (I5) 「決めてほしいこと」が曖昧（判断対象・期限が無い）
#      このブロックのスライドを目視で確認する候補を出す
grep -nE '決めていただきたい|ご判断ください|ご承認ください|判断のポイント' slides/*.html

# (I6) 結論が後ろに寄っていないか（前半 1/3 に「結論」相当の見出しがあるか）
perl -0ne '@s=/<div class="s\b[\s\S]*?(?=<div class="s\b|<\/body>)/g; $n=int(@s/3)+1;
  $hit=0; for $i (0..$n-1){ $hit=1 if $s[$i]=~/<h[12][^>]*>[^<]*(結論|方針|実績|進捗)/ }
  print "結論が前半 $n 枚に見当たらない — 構成を見直す\n" unless $hit' slides/*.html
```

**I6 がヒットしたら構成設計に戻る。** 結論が後半にある社内資料は読まれない。

---

## 7. 完了報告に含めること

1. 叩き台から書き直した見出しの一覧（旧 → 新）
2. 言葉遣いを直した箇所（過剰敬語の削除・依頼の具体化）
3. TODO ブロックの一覧
4. §6 の検査結果（特に I6）
