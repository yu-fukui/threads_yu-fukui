# full モード手順書

議事録・メモ・断片・テーマだけ、といった**構成が決まっていない入力**からデッキを作る。

このモードの肝は **構成を毎回ゼロから設計すること**。
用途テンプレート（`templates/<use>.md`）は「提案として成立するために必要な要素」のチェックリストであって、
並び順でも枚数でもない。**チェックリストを上から順にスライドにするのは禁止**（`core/structure.md` §1）。

---

## フェーズ A: 入力分析（内部処理・ユーザーには見せない）

### A-1. 材料の棚卸し

入力から次を抜き出す。**書かれていないことは書かれていないと判定する**（推測で埋めない）。

| 項目 | 見つかったか |
|---|---|
| 相手は誰か（社名・部署・役職） | |
| 相手が困っていること | |
| その原因 | |
| こちらが何をするか | |
| 費用 | |
| 体制・担当者 | |
| スケジュール | |
| 実績・事例 | |
| 相手にしてほしいこと | |

### A-2. 必須ブロックの充足判定

`templates/<use>.md` §1 の**必須ブロック**に対して材料が揃っているか確認する。
**過半が欠けていたら、SKILL.md §2-1 に従って材料を 1 問聞いて待つ。**

### A-3. 枚数の見積もり

`core/structure.md` §2 の目安から決める。材料の量で決めるのであって、テンプレートの項目数で決めない。

### A-4. 構成の設計

ここが本体。`core/structure.md` を読んで:

1. 材料を**内容のまとまり**に分ける（テンプレートの項目名で分けない）
2. まとまりごとに「このスライドで何を分からせるか」を 1 文で書く
3. その 1 文に対して**内容固有のレイアウト**を選ぶ（`core/structure.md` §8 のメタファー集）
4. **同じ体裁が 3 枚続いていないか**を並べて確認する。続いていたら 3 で選び直す
5. 必須ブロックのチェックリストと照合し、**抜けているものだけ**足す

**やってはいけない設計**:

- 「表紙 → 課題 → 解決策 → 次の一歩」を先に置いて、材料をそこに流し込む
- 1 ブロック = 1 枚で機械的に割り当てる
- 全部を 3 列カードで表現する

## フェーズ B: 構成の宣言（返事は待たない）

設計した構成を**数行で宣言してから、そのまま生成に進む**。

```
この構成で作ります（テーマ B・提案資料・スタイル formal・viz:low・全 12 枚）

  1  表紙
  2  問い合わせ対応の現状          … 受付から回答までの流れを 1 本の帯で
  3  時間がかかっている箇所         … 帯の 1 区間を拡大して内訳
  ...
 11  お見積もり                    … TODO（材料なし）
 12  次のステップ

違う場合は止めてください。そのまま生成に入ります。
```

- **返事を待たない。** 判断できる人は止められ、初心者は流れる
- TODO になる枚は宣言の時点で明示する
- 構成は `slides/<name>-structure.md` に保存する（後から直すときの土台になる）

### B-1. 構成ファイルの形式

```markdown
# 構成: <タイトル>

- テーマ: B / 用途: 提案資料 / 全 12 枚

## スライド 1: 表紙
- 役割: 何の提案か・誰宛か
- レイアウト: 大タイポ + 右下に日付
- 内容: ...

## スライド 2: 問い合わせ対応の現状
- 役割: 相手の現状を相手の言葉で示す
- レイアウト: 横一本の帯（受付 → 一次回答 → 担当者 → 完了）
- 内容: ...
```

## フェーズ C: HTML 生成

### C-1. 順番

1. `<head>` — テーマ定義の Google Fonts `<link>` と 16 変数を展開
2. スケーリング CSS（`core/rules.md` §11）
3. マーカーコメント（`core/rules.md` §11、v1.1 形式・style/viz 付き）
4. スライド本体を 1 枚ずつ
5. ナビゲーション JS（`core/rules.md` §11）

### C-2. 生成中に守ること

- **色はすべて `var()` 経由**。`#fff` のみ例外
- **`--accent` を文字色に使わない**（テーマ定義のコントラスト規約）
- 見出しに句点・飾り読点を入れない
- 提案資料なら見出しは**名詞型**（`templates/proposal.md` §3-1）
- 材料が無い必須ブロックは **TODO ブロック**として出す（`templates/proposal.md` §2）
- **1 枚書くたびに「直前の 2 枚と同じ体裁になっていないか」を確認する**

### C-3. 生成後の自己チェック

- [ ] 全スライドにマーカー相当の構造（`.s` クラス）があるか
- [ ] ページ番号が全枚に入っているか
- [ ] 横並びカードの下端が揃っているか
- [ ] 面ルールの許容枚数内か

## フェーズ D: iter-0 preflight（撮影前に必ず全件）

```bash
# 1. コア 21 項目
#    core/rules.md §12 のコードブロックを全件実行する

# 2. 面ルール検査
#    core/rules.md §12-1。テーマ定義の許容値と突き合わせる

# 3. 用途別の追加検査
#    templates/<use>.md §5 を全件実行する
```

ヒットは修正するか、例外として残す理由を完了報告に書けるようにする。
**「ぱっと見良さそう」で撮影に進まない。**

## フェーズ E: 視覚検証ループ

`core/validation.md` に従う。

- 全枚撮影・全枚目視。**サンプリング禁止**
- 上限 2 周（iter-0 → iter-1 → iter-2）
- **TODO ブロックを含むスライドは密度・余白チェックの対象外**
- フォント警告が出たらループを回さず、先に環境を切り分ける
